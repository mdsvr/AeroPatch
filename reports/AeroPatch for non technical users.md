# Give non-experts evidence, not verdicts

**Correction (2026-10-22, from the run files).** This report first said CWE-22, CWE-328 and CWE-918 were out of reach locally and should skip the model. That held only for the test split, which has one CWE-22 and one CWE-328 scenario. The untuned model fixed the held-out C-022-01 and C-328-01 in both Tier C runs (`20261014-132647`, `20261014-132909`, each `-repair-local-test_c`). So no class skips the model; the cards for classes it often misses say so. The plan in [docs/17-easy-use-part1.md](../docs/17-easy-use-part1.md) carries this and the other corrections from its recheck.

AeroPatch can be made usable by someone who will never read a diff, but the interface is the smaller half of the job. The harder half is that on a person's own folder the evidence behind every benchmark number goes missing. The product should give that person one install line and an `aeropatch doctor` that names each broken prerequisite in plain words. Next comes a read-only "check my project" that shows at most five findings as what-could-happen cards. Last is a fix flow that proposes one change at a time and labels it by what was actually checked ("the scanner no longer flags this and your existing tests still pass"), never "fixed". It applies a change only when asked, with a backup and a one-step undo, and stays local unless the user asks Claude through their own subscription. The 70% and 35% resolve rates were earned with the finding handed to the model and a hand-written exploit test feeding every repair. On user code neither exists. Without that test the sandbox's RESOLVED rule cannot fire at all. Bandit's precision on real Python was 11% in one 2026 study. And the flaw non-experts ship most, a hard-coded key, stops at AeroPatch's own secret filter. So the first phase builds almost nothing for users. It reruns AeroPatch's benchmark with the exploit tests hidden to measure how often each label is right, and scans the real-CVE repositories to see whether the scanners would find those bugs at all. Three building phases follow, each closed by measured numbers: label precision, triage recall, environment build rate, undo integrity, and a six-person review test that checks whether people reject a plausible but wrong fix. Expect most findings on real code to end as "not fixed" or "not proven". The product succeeds if it says so plainly.

## The 35% was earned with help a user's folder cannot give

The headline numbers are real but conditional. The untuned Qwen3.5-4B resolved **38 of 54 test runs (70%) and 7 of 20 real-CVE runs (35%)** on its own. The cascade that hands the third attempt to Opus 5.5 resolved 54 of 54 and 18 of 20 ([README](../README.md)). Three kinds of help sit inside those figures. First, the model is told which finding to fix. The loop calls this oracle localization ([loop.py](../src/aeropatch/agent/loop.py)). Second, every repair attempt is fed the failures of a hand-written proof-of-concept (PoC) exploit test, and that feedback is worth a lot: the repair loop adds **18 points** on test, from 52% at attempt 1 to 70% by attempt 3 ([README](../README.md)). Third, the hand-built scenarios are small, about 50 lines each, and each has regression tests written to catch a broken fix ([NOTES.md](../NOTES.md)). On a user's folder the finding comes from a scanner, no exploit test exists, and whatever tests exist were not written with this fix in mind.

Four facts in the code turn that gap into concrete work.

**The sandbox cannot report success without a PoC.** `parse_logs` marks a suite passed only when it ran at least one test, and RESOLVED needs the PoC suite to pass ([sandbox.py](../src/aeropatch/sandbox/sandbox.py)). An empty PoC slot therefore always reads as a failure.

**Detection on real code has never been measured.** All ten real-CVE (Tier B) findings come from advisories (`"tool": "advisory"`), not from a scanner, so nothing shows that Opengrep's 22 project rules or Bandit would find those bugs ([evaluations/scenarios](../evaluations/scenarios/); [README](../README.md)). What the scanners do find is mostly noise. On one 2026 Python dataset Bandit's precision was **11.34%** and Semgrep's 57.41% ([SAGA](https://arxiv.org/pdf/2601.15154)). An industrial study saw about **76% false alarms** ([Tencent, arXiv 2601.18844](https://arxiv.org/abs/2601.18844)).

**Secrets block the local route too.** `check_no_secrets` runs on every route except the oracle replay ([loop.py](../src/aeropatch/agent/loop.py); [prompts.py](../src/aeropatch/agent/prompts.py)). The CWE-798 scenarios the local model fixed twice used `"changeme"` precisely so that the filter would not fire ([NOTES.md](../NOTES.md); [per-CWE table](../docs/results/test/07-resolved-per-cwe.csv)). A real key next to the finding ends the run as SECRET_BLOCKED. Exposed secrets are among the most common flaws in apps non-experts ship: Escape counted more than 400 in its scan of vibe-coded apps ([Escape](https://escape.tech/blog/methodology-how-we-discovered-vulnerabilities-apps-built-with-vibe-coding/)), and a GitGuardian figure puts AI-assisted commits at a **3.2% secret-leak rate against a 1.5% baseline** ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-coding-assistant-attack-surface-2026040/)).

**Three vulnerability classes are weak spots locally.** Path traversal (CWE-22), weak password hashing (CWE-328) and SSRF (CWE-918) were never fixed by the local model in either test run ([README](../README.md)). That rests on one, one and two test scenarios, and the held-out CWE-22 and CWE-328 scenarios were fixed in both Tier C runs.

The research is equally blunt about what the weaker checks left on user code are worth. In Meta's AutoPatchBench, **61.1% of Gemini 1.5 Pro's patches built and stopped the crash, but only 5.3% were correct** ([Meta](https://engineering.fb.com/2025/04/29/ai-research/autopatchbench-benchmark-ai-powered-security-fixes/)). On SWE-bench, **29.6% of test-passing patches behave differently from the reference fix** ([PatchDiff](https://arxiv.org/html/2503.15223v2)). In Vul4Py, 12.6% of exploit-passing Python patches broke functionality ([Vul4Py](https://arxiv.org/html/2608.00692v1)). The one small-model Python repair paper reports 72-80% "fix accuracy" for 3-7B models, but it validates only by re-running Bandit, so the figure means "Bandit went quiet" ([SecureFixAgent](https://arxiv.org/html/2509.16275v1)). Bandit itself skips any line marked `# nosec` ([Bandit docs](https://bandit.readthedocs.io/en/latest/config.html)), and AeroPatch's gates already reject added suppression markers ([gates.py](../src/aeropatch/agent/gates.py)). With exploit checks, Qwen3-8B repaired **0 of 23** real Python CVEs, and most failures across models came from missing the vulnerable code (56.5-78.3%) ([VulnRepairEval](https://arxiv.org/html/2509.03331v1)). Generating the missing exploit test is no easy substitute either. Frontier systems build working proofs of vulnerability for **16-51%** of real bugs, and the top figure had the advisory and the fix as input ([FaultLine](https://arxiv.org/abs/2507.15241); [CVE-Genie](https://arxiv.org/html/2509.01835v1)). In one agentic testing study, about 44% of an agent's "this test exposes a bug" claims were wrong ([arXiv 2510.09907](https://arxiv.org/pdf/2510.09907)).

The honest end-to-end rate is therefore a product of four terms: the chance the scanner finds a real flaw, the chance triage ranks it into the five findings shown, the chance a fix succeeds, and the chance its label is right. Only the third has been measured, and only with help. The 35% must never appear in the interface as the chance that a displayed fix is correct. It answers a different question. A better principle for a non-expert tool comes from DARPA's AIxCC scoring, which shrank a team's whole score for inaccurate submissions ([Trail of Bits](https://blog.trailofbits.com/2024/01/18/our-thoughts-on-aixccs-competition-format/)): a wrong "fixed" costs more than an honest "could not check". "Not fixed, warning kept" has to be a normal, well-explained outcome, not an error screen.

## Non-experts need labels that name the check

The target user judges code by whether it runs, and the evidence says that judgement fails on security. AI coding is near universal: **83% of developers use AI at work** ([Stack Overflow 2026](https://stackoverflow.blog/2026/10/06/tales-from-the-2026-developer-survey-results/)). Across more than 100 models, the average security pass rate on generation tasks is 56%, and Python is the best language at 63% ([SD Times on Veracode 2026](https://sdtimes.com/agentic-security/veracode-finds-ai-generated-code-security-has-barely-improved-since-last-year/)). In a 2026 study of 100 participants, only **22% of submissions were fully secure**. Participants picked the least secure AI suggestion about as often as the most secure (35.0% against 37.7%) and spent about 21 seconds per suggestion. "Tests pass" was their most-used selection criterion ([Khalid et al.](https://arxiv.org/html/2609.21020v1)). Perry et al. found that participants with an AI assistant wrote less secure code on four of five tasks, yet rated their own answers as more secure on every one ([Perry et al.](https://ar5iv.labs.arxiv.org/html/2211.03622)). A green "tests passed" badge feeds the very cue that misleads these users. Status has to be stated as checkable evidence, with the unchecked part named beside it.

Shipped products have converged on the same shape, and it supports this choice. GitHub's agentic autofix, generally available since 15 October 2026, reruns CodeQL and opens a draft pull request carrying "a summary of the fix, why it closes the alert, and the validation steps Copilot took" ([GitHub changelog](https://github.blog/changelog/2026-10-15-agentic-autofix-for-code-scanning-alerts-general-availability/)). Codex Security's verify-fix step returns `fixed`, `still_vulnerable` or `inconclusive` "with supporting evidence and validation limits" ([Codex Security changelog](https://www.codex-docs.com/en/docs/security/plugin/changelog)). Aikido opens SAST pull requests only at medium or high confidence, at most two per repository per day and five files each, because a first scan "will typically discover a large amount of issues" ([Aikido help](https://help.aikido.dev/autofix-and-remediation/automation-and-merging/automatic-creation-of-pull-requests)). Lovable, the closest product built for founders, pairs plain-language explanations with a one-click "Try to fix" ([Lovable](https://lovable.dev/blog/a-founders-guide-to-lovable-security)). One community member warns, anecdotally, that its "Try to Fix All" button "often creates new problems" ([Facebook group](https://www.facebook.com/groups/lovableboost/posts/1298729689005961/)). After the 2026 Snowflake incident the Cloud Security Alliance advised treating "a clean AI review as one input among several rather than a sufficient control" ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-wiz-red-agent-copilot-snowflake-20260825-c/)). The survey behind these notes found no mainstream product that is both local by default and free for private code. The local open tools, Patchwork and Pixee's codemodder, do not validate with exploit tests ([autofix survey](../research_notes/AeroPatch%20for%20non%20technical%20users/autofix_products_ux.md)). That gap is AeroPatch's opening.

The label ladder below maps onto fields the sandbox and gates already record: the gate result, `regressions_passed` and `regression_total`, `lint_ok`, and `original_rule_present` from the host re-scan ([sandbox.py](../src/aeropatch/sandbox/sandbox.py); [loop.py](../src/aeropatch/agent/loop.py)). The core change is therefore a mapping function, not new machinery. That is the "smallest change" argument for the whole plan. Every label also requires that all eight deterministic gates passed.

| Label shown | What must hold | What the card says was not checked |
|---|---|---|
| **Attack test now blocked** (Phase 3 only) | A witness test frozen before any patch failed on the original code for the stated security reason and passes after. Every baseline-passing test still passes, and the scanner rule is gone. | "AeroPatch wrote this attack test itself"; other routes to the same flaw; behaviour your tests do not cover |
| **Scanner quiet, your tests still pass** | The original rule no longer matches the file, and every test that passed twice at baseline still passes | Whether an attack is actually blocked; behaviour your tests do not cover |
| **Your tests still pass; the scanner could not re-check this** | Every test that passed twice at baseline still passes, but the re-scan returned no answer (`original_rule_present` is None: an advisory finding, or an Opengrep finding with Opengrep missing). None never counts as "scanner quiet" | Whether the flaw is gone at all; behaviour your tests do not cover |
| **Scanner quiet, not tested** | The rule no longer matches; the project has no tests, or none ran | Everything about behaviour |
| **Not fixed, warning kept** | A gate or check failed and the attempts are used up | Shown with the failing check and the next step |
| **Probably not a real problem** (collapsed) | Triage judged a likely false positive | Kept, never deleted |

Two wording rules follow from the research. The first is to keep "secure", "safe", "fixed", "verified" and "guaranteed" out of status lines. In an 881-person study, verbal probability phrases in the 20-80% range were interpreted very inconsistently ([arXiv 1901.09686](https://arxiv.org/pdf/1901.09686)), and highlighting by raw model generation probability gave programmers no benefit over no highlighting at all ([Vasconcelos et al.](https://arxiv.org/abs/2302.07248v3)). The second is to attach to each label only a frequency measured on AeroPatch's own benchmark, in the form "on real bugs, fixes with this label were correct N of M times", once Phase 0 has produced it. The verification notes proposed "Likely fixed" for the middle rung. The human-factors notes ban "fixed" in status lines. Naming the check settles the conflict.

Triage and the card carry most of the value for a non-expert. Triage starts by merging findings that Opengrep and Bandit both report on one line. It then parks LOW-confidence Bandit hits and findings in test files, using Bandit's own `--confidence-level` filter ([Bandit man page](https://bandit.readthedocs.io/en/latest/man/bandit.html)). It ranks the rest by severity and by expected fix size, because PatchEval patches of 1-5 lines succeed **32.5% of the time against 7.7% for 20 or more** ([PatchEval](https://arxiv.org/html/2511.11019v1)). It shows the top five and collapses the rest. Google keeps a check only if its "effective false positive" rate stays under about 10% ([Sourcegraph on Google](https://about.sourcegraph.com/blog/code-security-at-google-find-fix-vulnerabilities-in-code)). Codex Security records a reason when a finding is dismissed and re-applies it only while that reason still holds ([Codex Security changelog](https://www.codex-docs.com/en/docs/security/plugin/changelog)). AeroPatch can copy that with a plain file keyed on the fingerprint `scanners.py` already computes ([scanners.py](../src/aeropatch/tools/scanners.py)).

Each card should follow NN/g's error-message guidance: plain words, a specific cause, a constructive remedy and codes hidden by default ([NN/g](https://www.nngroup.com/articles/error-message-guidelines/)). It runs in five parts: a headline in the user's terms ("someone could read any file on your computer through your upload page"), what could happen, whether it matters for this app ("only if the app is on the internet"), what the suggested change does, and what to do next. The rule ID, CWE, diff and logs sit behind a toggle for the **79% who rate source attribution as important** ([Stack Overflow 2026](https://stackoverflow.blog/2026/10/06/tales-from-the-2026-developer-survey-results/)). The cards should be fixed templates written once per rule, not model output, so that a 4B model never invents a risk claim.

Secrets get a deterministic card and no model call at all. The right fix is to move the value into an environment variable. The urgent step is to **rotate the key**, because changing the code does not undo an exposure that has already happened. The card names the line but never prints the value. Because `prompt.txt` is written to the run folder ([loop.py](../src/aeropatch/agent/loop.py)), anything written to disk needs the same redaction as anything sent.

The apply flow should be one finding at a time, with no "fix all" button. Users who edited AI suggestions more ended up with fewer vulnerabilities (β = −0.5) ([Khalid et al.](https://arxiv.org/html/2609.21020v1)). Cognitive-forcing steps reduce overreliance, but people dislike them ([Buçinca et al.](https://arxiv.org/pdf/2102.09692)). So each fix should ask one cheap question ("does your app need to load files from outside this folder?"), highlight the two or three lines that carry the security change, and end with two or three "try this yourself" checks. Apply should copy each changed file to `.aeropatch/backup/<timestamp>/` and offer `aeropatch undo`, rather than branching and committing. That keeps the documented promise that nothing in AeroPatch commits ([README](../README.md)).

The privacy statement "your code stays on this laptop" is true for the CLI and a local page, and should be scoped to them. LLM IDEs have been documented sending an environment file's contents to external services without confirmation ([arXiv 2607.26390](https://arxiv.org/pdf/2607.26390)). Escalation should therefore be a per-finding button. It shows a preview of the exact outgoing text, already passed through the secret filter. It also says plainly that the cascade sends the whole attempt history ([README](../README.md)). Many non-experts will not have Claude Code installed, so the free local path has to stand on its own.

## Running a stranger's project is the second wall

Before AeroPatch can test a fix on a user's code, it has to build that code's environment, and the literature shows wide variation in how often that works. On popular 2024 repositories that already had tests, Repo2Run with GPT-4o built **361 of 420 (86%)** to the point where pytest runs. Inferring requirements from imports with pipreqs managed 6% ([Repo2Run](https://arxiv.org/html/2502.13681v3)). On repositories chosen to be hard, a deterministic install script configured **62 of 391 candidates (15.9%)** ([EnvBench](https://arxiv.org/html/2503.14443)). In Multi-Docker-Eval, 20.06% of instances built with simple commands such as `pip install -r requirements.txt` ([Multi-Docker-Eval](https://arxiv.org/html/2512.06915)). The repair loop is what lifts the best systems: BootstrapAgent falls from 95.9% to 26.2% without it ([BootstrapAgent](https://arxiv.org/html/2605.15815)). A small model makes a poor planner, though. Single-shot, Qwen3-8B configured **8 of 329** EnvBench repositories against GPT-4o's 29 ([PIPer](https://arxiv.org/html/2509.25455)). The design that follows is deterministic first. The model stays out of the setup path entirely until the project's own measurements show which failures matter.

The cheapest ladder reads the version and dependency files uv and Railpack already understand. It picks Python from `.python-version`, then `requires-python`, then `runtime.txt` ([uv docs](https://docs.astral.sh/uv/concepts/python-versions/); [Railpack](https://railpack.com/languages/python)). It installs from a lockfile if one exists, otherwise from every `requirements*.txt`. It then installs pytest and maps common native packages to apt packages, such as libpq-dev for PostgreSQL drivers, from Railpack's published table. Building this image is the only step with network access. Even that step runs untrusted code, because pip build backends execute project code when building from source ([pip](https://pip.pypa.io/en/stable/reference/build-system/)). It should run without host mounts or secrets, as the current scenario build already does under `--require-hashes` ([scenario.Dockerfile](../docker/scenario.Dockerfile)). Every test run afterwards uses `--network none` ([Docker](https://docs.docker.com/engine/network/drivers/none/)). The image should be tagged by a hash of the repository's dependency files and reused, because recipe reuse saves time in every system that measured it. BootstrapAgent cut downstream build time by 22.3% ([BootstrapAgent](https://arxiv.org/html/2605.15815)).

AeroPatch's own runner needs adjusting before a user's test suite will even run. `run.sh` passes `-c /dev/null`, sets `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1`, starts Python with `-I`, caps each suite at 240 seconds and reads tests from `/opt/scenario/tests_*` ([run.sh](../docker/run.sh)). The container copies the repository into a 512 MB tmpfs with a 2 GB memory limit ([sandbox.py](../src/aeropatch/sandbox/sandbox.py)). Suites that depend on pyproject pytest settings, conftest plugins or pytest-django will fail collection. Folders that carry a `.venv` or data files will overflow the tmpfs. The smallest change keeps the tests baked read-only in the image, which preserves the guarantee that a candidate cannot edit them. It lets the project's pytest config through and excludes `.venv`, `node_modules` and similar folders from the workspace copy.

The baseline then runs twice. Tests that differ between runs are excluded as flaky, which is SWE-rebench's practice ([SWE-rebench](https://arxiv.org/html/2505.20411)). The pass-to-pass set is whatever passed both times. pytest's exit code 5 identifies "no tests collected" reliably ([pytest](https://docs.pytest.org/en/stable/reference/exit-codes.html)). For a folder with no tests, the fallback is `compileall` plus an import of each module, the closest analogue to EnvBench's imports-resolve check, and the label drops to "not tested". Failures should map to a handful of named classes, each with a plain sentence for the user. Test timeouts (40.7% of Repo2Run's failures), missing native libraries, Python-version mismatches, a needed database server (Django tests against PostgreSQL need one) and missing secrets cover most of them ([Repo2Run](https://arxiv.org/html/2502.13681v3); [Django](https://docs.djangoproject.com/en/stable/topics/testing/overview/)).

The laptop budget shapes the sequence. Per-repo environment images run 0.9-1.5 GB. One environment-building agent peaked at **7.4-7.7 GB of memory per run** ([Multi-Docker-Eval](https://arxiv.org/html/2512.06915)). AeroPatch's own runs have already died of memory exhaustion beside Ollama and Docker on this 16 GB machine. So builds and the baseline should run before the model loads, one build at a time, with the WSL VM's memory capped in `.wslconfig` as Docker advises ([Docker WSL](https://docs.docker.com/desktop/features/wsl/best-practices/)). Work folders should stay short to keep under Windows' 260-character MAX_PATH ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation)).

## One script, one doctor, one local page

All three prerequisites install through winget: `Docker.DockerDesktop`, `Ollama.Ollama` and `astral-sh.uv`. Only Docker needs admin rights. Its winget manifest installs for all users, elevates itself and always passes `--accept-license` ([Docker manifest](https://github.com/microsoft/winget-pkgs/blob/master/manifests/d/Docker/DockerDesktop/4.96.1/Docker.DockerDesktop.installer.yaml)), so a bootstrap script must ask before accepting on the user's behalf. Docker Desktop is free for personal use and for businesses with fewer than 250 employees and under $10 million revenue. It needs WSL 2.1.5 or later, 8 GB of RAM and hardware virtualization turned on in the BIOS ([Docker docs](https://docs.docker.com/desktop/setup/install/windows-install/)). The extracted Docker requirements also listed Windows editions inconsistently. The AeroPatch laptop itself runs Docker Desktop on Windows 11 Home ([install notes](../research_notes/AeroPatch%20for%20non%20technical%20users/install_and_interfaces.md)), which settles that question in practice. Ollama installs per user with no admin rights and needs at least 4 GB of disk for its binaries ([Ollama Windows](https://docs.ollama.com/windows)). The one step software cannot do for a non-expert is enabling virtualization in the firmware. Podman Desktop removes nothing here, because it needs WSL2 or Hyper-V as well ([OneUptime](https://oneuptime.com/blog/post/2026-03-18-install-podman-desktop-windows/view)). The doctor should detect this case and explain it, not try to automate it.

Packaging hides a trap. `ROOT` is computed as `Path(__file__).resolve().parents[2]` ([config.py](../src/aeropatch/config.py)), and the wheel packages only `src/aeropatch` ([pyproject.toml](../pyproject.toml)). So `uv tool install git+…`, the route the install notes suggest, would lose `rules/`, `docker/` and `.tools/opengrep`, and would write runs inside the tool's virtual environment. The smallest working route needs no packaging change. The bootstrap downloads AeroPatch's release zip at a tag with PowerShell's built-in web and archive commands, runs `uv sync` there, and fetches Opengrep checked against its release digest, as the CI job already does ([ci.yml](../.github/workflows/ci.yml)). Without Opengrep, the scan falls back to Bandit alone, the 11%-precision path. A frozen `.exe` should wait. Microsoft documents that unsigned apps get a "strong SmartScreen block". Its Artifact Signing service, about $9.99 a month, is open to individuals only in the USA and Canada. SignPath Foundation signs qualifying open-source projects for free ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)). Ollama's own `install.ps1` pins a version through `OLLAMA_VERSION` and checks the installer's Authenticode signature, which makes it a sound model for AeroPatch's script ([Ollama releases](https://github.com/ollama/ollama/releases)).

The doctor should copy `flutter doctor`'s shape: one line per area, a plain fix under each failure and a final "No issues found!" ([Codecademy](https://www.codecademy.com/article/check-your-flutter-installation-with-flutter-doctor)). Like Codex Security's readiness checks, each problem should be marked as blocking or as a warning ([Codex Security changelog](https://www.codex-docs.com/en/docs/security/plugin/changelog)). The standard library covers every check, and each has a documented failure behind it. `docker info` shows whether the engine is up, since Docker Desktop "does not start automatically after installation". `GET /api/version` shows whether Ollama is answering, which matters because a documented Windows bug leaves the tray icon visible while the server never starts ([ollama #18507](https://github.com/ollama/ollama/issues/18507)). `/api/tags` shows whether the model is present. Free disk and `nvidia-smi` cover the rest.

The doctor also has to guard against two kinds of model drift. The first is Ollama itself. It shipped **four releases between 14 and 21 October 2026** ([Ollama releases](https://github.com/ollama/ollama/releases)), and turning off its auto-download toggle stops downloads, not hourly version checks ([OpenVeil](https://openveil.app/blog/ollama-disable-automatic-updates-version-check)). So the doctor should warn when an update is staged in `%LOCALAPPDATA%\Ollama`. The second is the model tag. The library `qwen3.5:4b` that users will pull was rebuilt as `d8b0f5e9760c` and has not been benchmarked ([README](../README.md)), so the doctor should compare the local digest with whichever one Phase 0 measured.

The doctor should also report when a machine has no GPU. A Q4 4B model on a 4-core CPU runs at roughly 8-12 tokens per second in one guide ([ComputingForGeeks](https://computingforgeeks.com/install-ollama-rocky-ubuntu/)), against 46.5 on the RTX 3050 ([README](../README.md)). AMD cards can use Ollama's Vulkan path, which is on by default, though the Windows doc never mentions Intel ([Ollama Windows](https://docs.ollama.com/windows)). The 1.9 GB `qwen3.5:2b` ([Ollama library](https://ollama.com/library/qwen3.5/tags)) has no evidence on patch quality and should not be offered as a fallback until it has been benchmarked.

For the surface, a local page on the standard library's `http.server` is the only option that keeps the whole conversation local, needs no account and adds **zero packages**. Gradio would add 54, NiceGUI 48, Streamlit 35 and FastAPI with uvicorn 14 ([install notes](../research_notes/AeroPatch%20for%20non%20technical%20users/install_and_interfaces.md)). Because its buttons write files, the page should bind to 127.0.0.1 and require a per-launch token, so that no other web page can drive it. Claude Desktop's `.mcpb` bundles accept a `uv` server type in a bundle of about 2 KB ([MCPB](https://github.com/modelcontextprotocol/mcpb/blob/main/MANIFEST.md)), but two questions are open: whether Claude Desktop ships uv itself (its support article mentions only a built-in Node.js), and whether the free plan allows local extensions ([Claude support](https://support.claude.com/en/articles/10949351-getting-started-with-local-mcp-servers-on-claude-desktop)). Claude Desktop and Cursor also send the chat itself to a hosted model, and ChatGPT accepts only remote MCP servers ([OpenAI Help](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt)). The MCP server's allowlist is the benchmark folder alone, and its own comment names the one-line change that would widen it ([mcp_server.py](../src/aeropatch/mcp_server.py)). Widening it would send scan results, context and diffs into a hosted chat, so it belongs after the local page. When it happens, tool outputs should be redacted and the `remediate` choices limited to the local and `claude-code` configs, because `baseline-frontier` is the paid API-key route ([config.py](../src/aeropatch/config.py)).

## Four phases, each closed by a measured number

The order follows one rule: measure what a user's folder would actually get before building anything that shows it to them, then add the thinnest layer that delivers the next visible step. Each phase reuses the loop, gates, sandbox and scanners unchanged wherever it can.

| Phase | What a user gets | Smallest change that delivers it | Exit criteria (all must hold) |
|---|---|---|---|
| **0. Measure first** | Nothing new except `aeropatch doctor` | A label function over fields the sandbox already records. One repair-feedback line saying the scanner still flags the rule in that file, which the product loop uses too. Two config flags that drop the PoC suite (V1) or both suites (V2) from repair feedback and from the stop rule, then run the hidden suites once on the final diff. A stdlib doctor | Per-label precision published as N of M with 95% Wilson intervals, from V1 on test and Tier B and V2 on test, two runs each. Oracle replay through the labeller published, showing how many correct reference fixes each label misreads. The pulled library digest scores within 4 of 54 of the export (the project's pre-set bar), with the two run alternately on the same day, two runs each; otherwise the doctor warns on any other digest. Scan results on the 10 pristine Tier B repos published: findings per repo, and advisories with a finding within 3 lines. The doctor names each of six seeded faults correctly in a scripted test (Docker stopped, Ollama not answering, model missing or a different digest, a staged Ollama update, Opengrep missing, low disk) |
| **1. Check and fix a folder from the CLI** | `aeropatch check <folder>`: a read-only report of at most five cards. Then `fix`, `apply`, `undo` and `dismiss` | A Task built from a scan finding: allowed path is the finding's file, target from tree-sitter, an empty PoC slot, and the user's tests baked read-only as the regression suite. A deterministic dependency ladder in a networked build, with tests run offline. Baseline run twice. A fixed secrets card. A backup before apply. Cards for CWE-22 and 918, often missed on test, say so | Treating benchmark repos as user folders, the oracle replay gets the same label through both paths on 27 of 27 test scenarios, and repair-local through the folder path lands within 4 of 54 of V1, the two run alternately on the same day. The scenario's finding lands in the triaged top five for at least 25 of 27 test scenarios. On 10 small public repos at pinned commits, the build-and-collect rate and failure classes are published, and hand-labelled precision of the shown findings is at least 50%. Undo restores byte-identical files in every scripted case, and nothing is written before Apply. Review test (6 people, replayed outputs): at least 5 reject the plausible-but-wrong fix, 5 apply the good one and 5 restate a risk in one sentence, and all 6 can undo |
| **2. No terminal needed** | One PowerShell line installs everything; a desktop shortcut opens a local page with cards, diffs and Apply / Skip / Undo | An `install.ps1` that installs uv, Ollama at a pinned version, and Docker after an explicit licence prompt. It fetches a digest-checked Opengrep, pulls the measured model, downloads the release zip and runs `uv sync`. `aeropatch ui` on `http.server`, bound to 127.0.0.1, with a per-launch token | A fresh Windows 11 Home machine reaches an all-green doctor from the one line, with only the BIOS step manual; time recorded. Install test: at least 2 of 3 participants reach green unaided on their own laptops. Page test (6 people): the Phase 1 reliance bars hold and mean SUS is at least 68 |
| **3. Stronger labels and opt-in help** | "Attack test now blocked" on some findings; an "Ask Claude" button per finding with a preview of what is sent | Per-CWE witness templates filled by the local model, frozen before any patch, rejected unless they fail on the original for the stated reason, and placed in the existing PoC slot. Escalation through the existing `claude-code` route and secret filter | A witness gets built for a published share of the 27 test scenarios. Label 1's precision against the hidden human-written PoC beats label 2's point estimate; otherwise label 1 is not shipped. Cascade resolve rate under V1 published beside the 100% and 90% earned with PoC feedback. The adversarial split still blocks the credential before sending and lets 0 of 4 injections through |

Phase 0 is cheap because the benchmark already holds the ground truth, but one piece of the loop has to be built first. Today the next prompt receives only `junit.summarize` of the test-suite failures. The lint result, the in-sandbox Bandit result and `original_rule_present` are recorded but never fed back, and the loop stops only on RESOLVED ([loop.py](../src/aeropatch/agent/loop.py); [sandbox.py](../src/aeropatch/sandbox/sandbox.py)). Without a PoC, a model whose edit leaves the rule matching would therefore get no message about it. Phase 0 adds that one feedback line, and V1 and V2 must use exactly the loop the product will ship, or the measured precision belongs to a different loop. In V1 the loop then sees regression failures and the re-scan line, and stops at "scanner quiet, your tests still pass". Only after it stops does the hidden PoC run on the final diff, so precision means "this label and the human exploit test agree". The hidden suite must stay out of both the feedback and the stop rule, or the measurement leaks. Following the README's rule that changing a value means a new config name, V1 and V2 get configs of their own ([config.py](../src/aeropatch/config.py)).

V2 matters more than it looks. The benchmark's regression tests were written for each scenario and are far stronger than what most users have. Without V2, the measured precision of "your tests still pass" would flatter the label most users actually receive. Tier B under V1 measures something specific. The scanner cannot re-check advisory findings, so those runs stop when the regression tests pass and earn "your tests still pass; the scanner could not re-check this". Its precision shows how much passing tests alone are worth on real projects. Both variants also yield a resolve rate under realistic feedback, and that rate, not 35%, is the one to quote to users.

At 27 and 10 tasks, two runs each, the intervals will span 20-40 points ([README](../README.md)). They should be shown as "N of M" counts, not percentages. The oracle replay shows the other direction of error: correct reference fixes that the scanner still flags, which the ladder would call "not fixed". The runs are long, unattended jobs on a 16 GB laptop. They should start resumably with `--run-id`, only after checking Ollama's logs for a staged update, and with nothing heavy running beside them.

The usability tests follow the protocol in the human-factors notes. Recruit two groups of three, such as solo founders who build with AI tools and students, because five users find about 85% of the problems in one group and three rounds of five beat one round of fifteen ([NN/g](https://www.nngroup.com/articles/why-you-only-need-to-test-with-5-users/)). Each session is a 45-minute think-aloud on a seeded Flask app with four or five findings. Its outputs are replayed from a fixed recording, so every participant sees the same good fix, the same plausible-but-wrong fix (it passes the re-scan but breaks a feature), the same "not fixed" case and the same secrets card, and no model has to run on a participant's machine. The key measure is appropriate reliance, meaning the good fix applied and the bad one rejected, adapted from the Khalid and Perry study designs. Beside it go task success, self-rated confidence against correctness, comprehension, whether participants ran the manual checks, and the System Usability Scale, where 68 is the average across about 500 products ([MeasuringU](https://www.measuringu.com/sus/)). The install test is kept separate and run on participants' own laptops, because a failed Docker install there would otherwise wreck the review session.

The plan defers the following on purpose, each with the evidence that would bring it back.

| Deferred | Why not now | Revisit when |
|---|---|---|
| An LLM repair loop for environment setup | Single-shot, Qwen3-8B configured 8 of 329 hard repos ([PIPer](https://arxiv.org/html/2509.25455)); more memory pressure beside Docker | Phase 1's failure classes show resolver conflicts dominate and escalation is available |
| Database or Redis sidecars, private indexes, required secrets | Each adds a moving part; Django tests against PostgreSQL need a reachable server ([Django](https://docs.djangoproject.com/en/stable/topics/testing/overview/)) | "Needs a database" is the most common blocker reported in Phase 1 |
| Benign-input differential tests with Hypothesis Ghostwriter | Untested on security patches; the docs call its output a "starting point for human authorship" ([Hypothesis](https://hypothesis.readthedocs.io/en/latest/reference/integrations.html)) | V2 shows "scanner quiet, not tested" is the weakest label in use |
| Deterministic codemods (codemodder-python) | A new dependency; coverage of AeroPatch's rules unchecked ([Pixee docs](https://docs.pixee.ai/open-source/codemodder/)) | A class the 4B never fixes has a matching codemod |
| Claude Desktop, Cursor or `.mcpb` access | The chat runs on a hosted model; uv and free-plan support unconfirmed | After Phase 2, with redacted outputs and configs limited to local and `claude-code` |
| A signed `.exe`, MSIX or winget manifest | SmartScreen blocks unsigned apps; individual signing is US/Canada only ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)) | The one-line install fails the Phase 2 bar |
| PR bots, a GitHub Action, pre-commit hooks, an Explorer menu entry | Need a server, paid GPU runners ([GitHub](https://docs.github.com/en/actions/reference/runners/larger-runners)) or a signed sparse package | Not on the non-expert path |
| Podman, macOS, Linux; a 2B or CPU-tuned model; fine-tuning | Untested, unproven, or measured to lose or tie ([README](../README.md)) | A benchmark run on that platform or model |
| Multi-file, source-side and dependency-upgrade fixes | The gates cap edits at 3 files and 60 lines ([config.py](../src/aeropatch/config.py)) | Label calibration holds on single-function fixes |

## Conclusion

The most transferable thing this plan produces is a measurement, not a feature. Per-label precision, taken from AeroPatch's own benchmark with the exploit tests hidden, turns a research harness into an interface string a non-expert can trust: "fixes with this label were right N of M times". No product in the survey publishes that number for its own labels, and GitHub has published no acceptance or regression data for its autofix at scale ([Tech Insider](https://tech-insider.org/github-ai-autofix-ga-codeql-2-27-2026/)). The measurement also decides the product's shape ahead of time. If V2 shows that "scanner quiet, not tested" is right only a minority of the time, then for a user without tests AeroPatch is an explainer that offers suggestions, not a fixer. Phase 1's read-only check, triage and deterministic secrets card are still worth shipping on their own.

The bottleneck order changes too. For a non-technical user the model is the third problem, after detection and triage (which real flaws reach the five cards) and environment (whether their project runs in the sandbox at all). Both can be measured without a single model call, so the cheapest gains sit there. They also rest on deterministic work AeroPatch already does well. The local model fixing a minority of real findings is acceptable, so long as every other finding leaves with an honest label, a reason and a next step.
