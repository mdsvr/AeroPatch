## 1. LangGraph vs plain Python

LangGraph is mature (1.0 in Oct 2025, 1.2 in May 2026, reported). Its selling points are
durable execution, checkpointing, human-in-the-loop interrupts, and branching multi-agent graphs.
AeroPatch doesn't need any of them:

| LangGraph feature | Needed here? | Plain alternative |
|---|---|---|
| Durable checkpointing | Only to resume benchmark runs | Skip task IDs that already have a `RunResult` in the JSONL |
| Human-in-the-loop interrupts | Only before a PR | A separate CLI command, `aeropatch submit` |
| Parallel branches | No; one edit at a time on a 4 GB GPU | — |
| Multi-agent graphs | No; the pipeline is fixed (doc 05) | — |

**Decision**: write a plain Python state machine in `loop.py` (~120 LOC, stdlib only). It's
easier to debug, test, and explain in an interview. If you want LangGraph on the resume later,
porting a 6-state loop takes a day. Do it only after the benchmark numbers exist.

`asyncio` isn't needed in the loop either. Generation is sequential on one GPU. The only real
concurrency is in the benchmark runner (≤2 sandboxes), and a `ThreadPoolExecutor(max_workers=2)`
covers it.

## 2. States and transitions

| State | Does | Next |
|---|---|---|
| `INTAKE` | Validate the `Task`; load the scenario image | `LOCALIZE` |
| `LOCALIZE` | Finding → file/function; build `Context` (doc 06) | `GENERATE` (or `FAILED:LOCALIZATION` if nothing found) |
| `GENERATE` | Router picks a route; the model returns text; parse it into `EditProposal` | `GATE`, or `GENERATE` on parse failure (counts as an attempt) |
| `GATE` | Deterministic checks (part 2) | `VALIDATE`, or `GENERATE` with violation feedback |
| `VALIDATE` | Sandbox: apply, PoC, regressions, lint, re-scan (doc 07) | `DONE:RESOLVED` or `REPAIR` |
| `REPAIR` | Build the feedback from the trimmed failure summary | `GENERATE`, or `DONE:FAILED` when the budget is spent |

```text
for n, route in enumerate(attempt_plan, 1):          # e.g. [local, local, frontier]
    proposal = generate(route, task, context, history) # refusal -> log, next route (not numbered)
    gate = check(proposal, task)
    result = validate(task, proposal) if gate.ok else None
    history.append(Attempt(n, route, proposal, gate, result))
    if result and result.resolved: return RunResult(resolved=True, ...)
    if over_budget(history): break
return RunResult(resolved=False, ...)
```

## 3. Definition of "resolved" (write it down once, use it everywhere)

A scenario counts as **resolved** only when all four hold:
1. The edit parsed and applied cleanly.
2. Every gate passed (no forbidden paths, no test edits, size limits respected).
3. **All PoC tests pass**. They failed on the original code, so this shows the vulnerability is fixed.
4. **All regression tests pass**, which shows behaviour was preserved.

Tracked separately, not part of "resolved": the original scanner finding cleared, no new
scanner findings, and lint clean. Scanners have false negatives and false positives, so they
make poor ground truth.

## 4. Budgets (stop conditions)

| Budget | Default | Why |
|---|---|---|
| Max attempts per scenario | 3 (first attempt plus 2 repairs) | Matches the plan; gains flatten after 2 repairs |
| Max output tokens per attempt | 1024 local / 4096 frontier | Edits are short; stops runaways |
| Max frontier spend per scenario | $0.50 | Hard cost ceiling for benchmark sweeps |
| Max wall clock per scenario | 10 min | Stops a slow sandbox from blocking an overnight run |
| Max context tokens (local) | ~6k | Past that, escalate or trim (doc 04) |

All budgets live in one config dict, and a run's budgets are written into its JSONL header.

## 5. Edit format: search/replace blocks, not raw unified diffs

The plan asks the model to output unified diffs. That's the single most avoidable failure
source for a small model:
- Hunk headers need exact line numbers and counts, and small models get them wrong.
- Context lines must match byte for byte, which is easy to break with whitespace.
- Aider's edit-format benchmarks, and 2025–2026 papers on edit representations, find
  search/replace blocks at or near the top for solve rate. Weaker models fail to produce
  mechanically applicable diffs much more often.

**Decision**: the model outputs search/replace blocks. The harness computes the unified diff
with `git diff` after applying them. The pipeline still produces a standard `.patch` file,
so the plan's "Candidate Patch (Diff)" box stays the same, but the diff is generated by code.

Format (one or more blocks, nothing else except an optional short rationale):

```text
RATIONALE: Use a parameterized query instead of string formatting.
<<<<<<< SEARCH app/db.py
    cur.execute(f"SELECT * FROM users WHERE name = '{name}'")
=======
    cur.execute("SELECT * FROM users WHERE name = ?", (name,))
>>>>>>> REPLACE
```

Why markers rather than JSON: code inside JSON strings has to escape quotes, backslashes and
newlines, and small models often get that escaping wrong. Use one format for local and frontier
models alike. It means one parser, and the fine-tuning data matches inference exactly.

## 6. Applying edits (`edits.py`)

For each block, in order:
1. The `path` must exist in the scratch worktree. New files aren't allowed in v1.
2. **Exact match** of the SEARCH text: exactly one occurrence means replace it.
3. With zero exact matches, try a **whitespace-tolerant match**: ignore trailing spaces,
   normalize line endings, and try with the common indent removed and re-added. Exactly one
   match means replace it, keeping the file's original indentation.
4. With zero matches after that, fail with `SEARCH_NOT_FOUND`. The feedback includes the
   closest lines from the file (`difflib.get_close_matches`), so the next attempt can copy
   them exactly.
5. With more than one match, fail with `SEARCH_AMBIGUOUS` and ask for more surrounding lines.
6. After all blocks apply, run `git diff` to get the unified diff, and store it on the attempt.

These apply failures turn into feedback at the `GENERATE` step, so the model gets a
cheap retry without a sandbox run.

## 7. Temperature and sampling per attempt

- Attempt 1: temperature 0.2, for a stable pass@1.
- Repair attempts: temperature 0.4, a little diversity so the model doesn't repeat the same
  wrong edit.
- A repair attempt whose edit is identical to a previous one is detected by hashing the
  normalized edits. Retry it once at temperature 0.8; if it's still identical, stop early and
  label the run `STUCK`.
