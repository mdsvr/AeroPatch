# 11 — Benchmark Harness and Evaluation Set (built in Weeks 1–2, run in Week 4)

Maps to: `src/aeropatch/bench.py` (`aeropatch bench`), `src/aeropatch/scenario.py` (validator), `evaluations/scenarios/`. Back to: [00-overall-plan.md](00-overall-plan.md)

## 1. Why evaluation moves to Week 1

The plan builds the benchmark in Week 4, after fine-tuning. That means the fine-tuned model
has nothing to be compared against. The claim that matters is the size of the delta: untuned
SLM vs fine-tuned SLM vs frontier, all on the same scenarios. Order of work:
- **Week 1**: scenario format, the first 10 scenarios, and a zero-shot baseline for 2–3 models.
- **Week 2**: grow to 40–50 scenarios, and run baselines with the full repair loop.
- **Week 3**: fine-tune; select checkpoints on dev scenarios only.
- **Week 4**: final runs on test scenarios, ablations, and reporting. No new scenarios.

## 2. Existing benchmarks: fit for this project

| Benchmark | Languages | Execution-verified | Fit | Notes |
|---|---|---|---|---|
| **PatchEval-Verified** (ByteDance) | Go, JS, Python | Yes, Docker + strengthened PoC tests | **Good (Python subset)** | 230 CVEs; ~500 GB for all images, 16+ cores recommended. The original paper's best was 23% (Nov 2025); the Jul 2026 leaderboard reports 80%+ for top models |
| **Vul4Py** (arXiv 2608.00692, Aug 2026) | Python | Yes: paired exploit + pytest functional oracles | **Very good** | 100 vulns, 60 projects, 60 CWEs, 2017–2025; its paired oracle rejected 15 of 119 patches an exploit-only oracle accepted (reported). Pre-2026 CVEs, so check for contamination |
| **CVE-Bench** (Gatti; "real-world CVE patching") | Python | Yes | **Good** | 20 CVEs from 18 projects, late 2025–early 2026: after most base models' training data |
| CVE-Bench (Wang, Liu, Xiao; NAACL 2025) | 4 languages | Yes (repair env) | Medium | 509 CVEs, 120 repos; SWE-agent best ~21% (reported); a repair benchmark with the same name |
| CVE-Bench (Zhu et al., UIUC Kang lab; ICML 2025) | Web apps | Exploitation | No | 40 critical CVEs; measures *exploiting*, not patching; out of scope |
| SEC-bench (NeurIPS 2025) | C/C++ | Yes (sanitizers) | No | Wrong language; needs a sanitizer toolchain, not pytest |
| SWE-bench Verified | Python | Yes | No | Bug fixes, not vulnerabilities; contaminated; OpenAI stopped reporting it |
| SWE-bench Pro | Multi | Yes | Low | Harder general software-engineering tasks; not security-focused |

At least three different benchmarks are called "CVE-Bench", so always say which one you mean.
The per-language split of PatchEval-Verified isn't stated in the sources checked; count the
Python cases from its Hugging Face dataset. Vul4Py's paired-oracle design is independent
support for this plan's PoC + regression test rule.

## 3. The AeroPatch evaluation set (target 40–50 scenarios)

| Tier | Count | Source | Purpose |
|---|---|---|---|
| **A: hand-built** | 25–30 | Small Python apps you write with one planted CWE each. Week 1's 10 are stdlib-only (sqlite3); Flask/FastAPI ones need a hash-pinned lockfile | Contamination-free, fully controlled, fast |
| **B: real CVEs** | 10–15 | Python cases from Vul4Py, PatchEval-Verified and CVE-Bench (Gatti), preferring those published after March 2026 | External validity |
| **C: held-out synthetic** | 5 | Generated by the doc 09 pipeline but never used in training, from different repos | Checks in-distribution generalization |

**test = the rest** (touched only in final runs). Record the split in `scenarios/split.json`.

## 5. Scenario anatomy (`evaluations/scenarios/<id>/`)

- `repo/`: the vulnerable project at a pinned commit (git submodule or tarball + commit hash).
- `scenario.json`: `id`, `tier`, `cwe`, `finding` (as a scanner would report it),
  `description`, `allowed_paths`, `poc_tests`, `regression_tests`, `split`, `published_date`
  (Tier B), `source_url`, and `license`.
- `tests_poc/`: tests that **fail on the vulnerable code and pass on a correct fix**. They check
  behaviour: the injection payload is treated as data, the traversal is rejected. They must not
  check the implementation, so a different correct fix still passes.
- `tests_regression/`: tests that pass **both before and after**. They stop "fixes" that delete
  the feature, e.g. a login must still work for valid users.
- `reference_fix.patch`: one known-good fix, used only to validate the scenario, never shown
  to models.
- `requirements.lock`: hash-pinned dependencies for the build phase (doc 07).

**Worked example: `A-089-01` (CWE-89, easy variant)**
- App (as built): a 19-line sqlite3 module, `app/db.py`, with `find_user(conn, name)` building
  `f"SELECT id, name FROM users WHERE name = '{name}'"`.
- PoC test: create users `alice` and `bob`, then call `find_user("x' OR '1'='1")`. It must
  return no rows, and it must not raise. On the vulnerable code it returns every user, so it
  fails. On a parameterized fix it returns nothing, so it passes.
- Regression tests: `find_user("alice")` returns alice; an unknown name returns empty; a name
  containing a legitimate apostrophe (`o'brien`) is found once inserted. That last one catches
  "fixes" that strip quotes instead of parameterizing. A fifth test adds then finds a user.
- Harder variant `A-089-02`: the query is assembled in a helper `build_filter(**kw)` in another
  module, and the finding points at the `execute` call. The model has to realize the fix
  belongs in the helper, which `allowed_paths` permits.

## 6. Scenario validation (automated, run in CI of the repo itself)

Each scenario must pass all four of these, or it doesn't enter the benchmark:
1. On vulnerable code: the PoC **fails**, regressions **pass**.
2. With `reference_fix.patch`: the PoC **passes**, regressions **pass**.
3. With a **"delete the function body"** patch: at least one regression test **fails**,
   which shows the regression tests catch destructive fixes.
4. The scanner finding is reported on the vulnerable code (Tier A), so the intake path is real.
   A Tier B finding comes from the advisory, so the validator marks this check as skipped.

## 7. Evaluation settings (the axes of the results table)

| Axis | Values |
|---|---|
| Model | Untuned SLM(s), fine-tuned SLM (Q4/Q5/Q8), frontier reference(s) |
| Routing mode | `local`, `frontier`, `cascade` (doc 04) |
| Repair loop | off (1 attempt) / on (up to 3) |
| Localization | **oracle** (given the ground-truth function) / **tool** (from scanner + tree-sitter) |
| Decoding | greedy (pass@1) / sampled n=5 (pass@k, doc 12) |
| Grammar constraint | on / off (local only) |

The full grid is too big for a laptop. Run all models × {repair on/off} × oracle localization
as the main table, and the other axes as focused ablations on the fine-tuned model only.

## 8. Harness mechanics (`aeropatch bench`, `src/aeropatch/bench.py`)

- Inputs: config name, scenario split, and output directory. The config fixes model, mode,
  budgets, seeds and temperature.
- For each scenario, call the same `loop.run(task, config)` the CLI uses, and append the
  `Attempt` and `RunResult` lines to `runs/<run_id>.jsonl`.
- Resumable: completed task IDs are skipped. Deterministic order (sorted IDs); seeds are logged.
- Concurrency: sequential generation, at most 2 sandboxes (doc 02). As built: `--jobs 2` runs
  two tasks at once with local generation under one lock; the default is `--jobs 1`, which the
  baseline runs use so that latency and tok/s stay comparable.
- The run header records the git commit of AeroPatch, model digests, image digests, server
  version, and hardware info, so every number in the README traces back to a run file.

## 9. Runtime and cost estimate for the Week 4 final runs

About 35 test scenarios × up to 3 attempts × 5 main configs gives ~525 generations and
~525 sandbox runs. Locally that's roughly 3–6 hours per SLM config, run overnight. Week 1
measured $0.018 per Tier A attempt on `claude-opus-5` (doc 04 §4), so a frontier config costs
about $2 on Tier A at 3 attempts; Tier B contexts are larger. On the `claude-code` route it's
subscription usage instead. pass@5 sampling
multiplies generations by 5, so run it on the fine-tuned SLM and one frontier model only.
